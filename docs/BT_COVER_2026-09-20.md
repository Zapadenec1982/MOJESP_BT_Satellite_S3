# Bluetooth cover art — 2026-09-20

Customer requested completing Bluetooth album artwork, authorized work on both

## Implementation

Protocol 1.5 adds COVER_RESET 0x17 (nonzero boot nonce + track generation) and
COVER_DATA 0x18 (same pair, total length, byte offset, <=1000 JPEG bytes).
Old layouts remain unchanged. Host bit 1 is accepted only with minor >=5;
legacy untagged COVER is not consumed. Both contract copies are identical.
A reset clears only Bluetooth artwork, cancels incomplete assembly and invalidates
pending decode publication. Old queued data cannot overwrite the new track.

ESP32 connects OBEX when the phone advertises the Cover Art feature, then requests
metadata again. It requests only linked thumbnails, retains the OBEX session,
collects at most 48 KiB and transfers ownership of the completed JPEG to a separate
low-priority sender. No UART pacing waits remain in the BTC callback. The sender
cancels on track change/capability loss/2-second queue stall. Only one outgoing
image is owned; no new OBEX image is fetched while that sender owns the buffer.
An in-flight old OBEX response is drained and discarded after a track change.
Malformed/absent image handles, failure or allocation limits leave an empty tile.

P4 assembles contiguous data into PSRAM, rejects gaps/duplicates/inconsistent sizes,
limits images to 256 KiB and drops an incomplete tail after 5 seconds. A separate
worker decodes JPEG, leaving the module/UART task available for control messages.
File and Bluetooth have independent 150-pixel tiles. A shared decoder mutex
serializes JPEG/PPA work; publication and clearing use a short critical section,
and generation is checked again after decoding. Progressive fallback dimensions
are now bounded to the same 2048x2048 ceiling as the hardware path.
The screen selects the tile for source 3 (Bluetooth), 4 (file), otherwise empty.

Two additional faults found in exact pinned IDF sources and application code:

1. ESP32 link TX used a driver ring. IDF uart.c::uart_tx_all loops without a wait
   when xRingbufferGetCurFreeSize returns zero. Our link sender priority exceeds
   the core-1 A2DP decoder priority. A long image can therefore starve decode,
   then release a burst of queued PCM. Changed only LINK_TX_BUF to zero: the
   documented unbuffered driver path waits on tx_fifo_sem. Application queues
   remain, so Bluetooth callbacks do not wait on UART. No shared IDF edit.
2. P4 requested JPEG_DEC_RGB_ELEMENT_ORDER_RGB. jpeg_types.h documents this as
   big endian; jpeg_dec_config_dma_csc swaps the two RGB565 bytes. PPA and LVGL
   use native little endian. Select the documented BGR setting (little endian).
   This is byte order for RGB565, not swapping red and blue in the UI.
   Also replace unconditional 16x16 output alignment with actual MCU geometry:
   YUV444 8x8, YUV422 16x8, YUV420 16x16, as jpeg_parse_sof_marker implements.
   Validate decoder output byte count before PPA and fall back to software on
   mismatch/unsupported grayscale. Log actual DMA dimensions and sampling mode.
